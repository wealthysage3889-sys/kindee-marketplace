## 3. Backend Token Verification Flow

### 3.1 Current Middleware (`middleware/auth.js:11-83`)

```javascript
export const verifyToken = async (req, res, next) => {
  const authHeader = req.headers.authorization;
  if (!authHeader?.startsWith('Bearer ')) return 401;
  
  const token = authHeader.split(' ')[1];
  
  // PRIMARY: Supabase JWT verification
  const { data: { user }, error } = await supabaseAuth.auth.getUser(token);
  
  if (error || !user) {
    // ❌ FALLBACK: Custom JWT verification (LEGACY)
    try {
      const decoded = jwt.verify(token, JWT_SECRET);
      req.user = decoded;
      req.accessToken = token;
      req.supabase = createUserClient(token);
      return next();
    } catch (jwtError) {
      return 401;
    }
  }
  
  // Supabase success path
  const { data: profile } = await supabaseAdmin
    .from('profiles').select('*').eq('id', user.id).single();
  
  req.user = { id: profile.id, email: profile.email, name: profile.name, ... };
  req.accessToken = token;
  req.supabase = createUserClient(token);
  next();
};
```

## 5. Facebook Login — Evidence-Based Approach

### 5.1 Frontend Token Type (Verified)

**Login.jsx lines 129-150, Register.jsx lines 140-158:**
```javascript
FB.login((response) => {
  if (response.status === "connected" && response.authResponse?.accessToken) {
    // Sends: response.authResponse.accessToken
    // This is a Facebook **Graph API Access Token** (opaque string, ~100-200 chars, NO periods, NOT a JWT).
  }
}, { scope: "public_profile,email" });
```

**Finding:** Frontend uses **Facebook JS SDK** → returns a **classic Graph API Access Token only** (no OIDC ID Token available via this SDK).

### 5.2 `signInWithIdToken` with Facebook Access Token — NOT Supported for JS SDK (Verified against official docs)

The official Supabase Facebook guide and `signInWithIdToken` reference document passing a Facebook access token to `signInWithIdToken({ provider: 'facebook', idToken: accessToken })`, but that guidance is **Flutter/native-specific** (`flutter_facebook_auth`) and only works when the SDK mints an actual OIDC ID token (iOS Limited Login / first authorization).

**Official evidence (Supabase):**
- `signInWithIdToken` strictly requires an **OIDC ID Token (JWT)**, not a Graph API access token. Passing a classic access token throws `400 Bad ID token` / fails at signature/JWKS or audience verification.
- Supabase auth issue #1522 (open): `Bad ID token` on Facebook `signInWithIdToken` is a known, unresolved issue. The Supabase team confirmed Firebase and Auth0 both exchange the **classic access token server-side**, not a native id token.
- Supabase auth PR #2609 (open, not released): proposes a server-side token-exchange grant (`/debug_token` verification) for Facebook access tokens — confirms server-side Graph API verification is the required path until it ships.

**Conclusion:** The existing Facebook JS SDK flow (access token → server-side `debug_token` + Graph API `/me`) is **NOT replaceable by `signInWithIdToken`** and is the correct, evidence-based approach. Method A (Graph API) is **VERIFIED CORRECT** and must be kept.

### 5.3 Decision: **Method A (FB SDK + Graph API)** — Verified Correct

| Approach | Frontend | Backend Verification | Verdict |
|----------|----------|---------------------|---------|
| **A: FB SDK + Graph API** (Current plan) | `FB.login()` → Access Token | `debug_token` + `/me` API (server-side) | ✅ **VERIFIED CORRECT** — keep |
| **B: `signInWithIdToken({provider:'facebook'})`** | JS SDK access token | Supabase `signInWithIdToken` | ❌ **NOT SUPPORTED** — JS SDK returns access token, not OIDC ID token; known open issue #1522 |
| **C: Supabase Native OAuth** | Redirect to `/authorize?provider=facebook` | `exchangeCodeForSession(code)` | Possible but changes UX; not required |

**Justification:**
1. Frontend already has FB SDK integrated (`SocialAuth.jsx`, `Login.jsx`, `Register.jsx`).
2. `signInWithIdToken` cannot consume a Graph API access token (verified above).
3. Method A allows immediate verification via `debug_token` + `/me` API.
4. Do **not** replace with `signInWithIdToken` — official docs + open issues demonstrate replacement would break the JS SDK flow.

**Implementation in authService.js:**
```javascript
case 'facebook':
  // 1. Verify token via debug_token (server-side, app secret never exposed to client)
  const debugRes = await fetch(
    `https://graph.facebook.com/debug_token?input_token=${accessToken}&access_token=${appId}|${appSecret}`
  );
  // 2. Get profile via /me

    `https://graph.facebook.com/me?fields=id,name,email,picture.type(large)&access_token=${accessToken}`

  // 4. Return Supabase session tokens
```

### 6.2 LINE Custom OIDC Compatibility — UNVERIFIED / NOT COMPATIBLE AS-IS (Web Login)

**Official documentation findings:**

| Item | Value | Source | Status |
|------|-------|--------|--------|
| LINE issuer | `https://access.line.me` | LINE Login docs (verify-id-token) + `.well-known/openid-configuration` | ✅ Verified |
| OpenID Discovery URL | `https://access.line.me/.well-known/openid-configuration` | LINE Login docs | ✅ Verified |
| Authorization endpoint | `https://access.line.me/oauth2/v2.1/authorize` | LINE Login docs | ✅ Verified |
| Token endpoint | `https://api.line.me/oauth2/v2.1/token` | LINE Login docs | ✅ Verified |
| JWKS URI | `https://api.line.me/oauth2/v2.1/certs` | LINE Login docs | ✅ Verified |
| Verify ID token endpoint | `POST https://api.line.me/oauth2/v2.1/verify` (`id_token` + `client_id`) | LINE Login docs | ✅ Verified |
| ID-token `iss` claim | `https://access.line.me` | LINE Login docs | ✅ Verified |
| ID-token `sub` claim | LINE user ID | LINE Login docs | ✅ Verified |
| ID-token `aud` claim | Channel ID | LINE Login docs | ✅ Verified |
| Signing algorithm — web login | **HS256** (HMAC with channel secret) | LINE Login docs: "for web login, HS256 is returned" | ✅ Verified |
| Signing algorithm — native/LIFF | **ES256** (ECDSA P-256, JWKS, `kid` header) | LINE Login docs | ✅ Verified |
| Discovery doc `id_token_signing_alg_values_supported` | `["ES256"]` only | LINE `.well-known/openid-configuration` | ✅ Verified (advertises ES256 only) |
| `email` claim present | Only when `email` scope granted AND user has verified email | LINE Login docs | ✅ Verified |

**Critical incompatibility (UNVERIFIED for Supabase Custom OIDC, strongly indicated by evidence):**

Supabase Custom OAuth/OIDC Providers verify ID tokens against the provider's **JWKS** (per official Supabase custom-oauth-providers docs). LINE web-login ID tokens are signed **HS256 with the channel secret**, not ES256/JWKS. The LINE discovery document advertises only ES256, so a relying party that trusts the discovery doc and verifies via JWKS will **fail** on web-login HS256 tokens.

- Supabase auth PR #2578 (open, **not released**): adds LINE as a built-in provider that verifies the ID token with **HS256 using the channel secret**, validates issuer `https://access.line.me`, audience (channel ID), and expiry. Web (authorization-code) flow only; native id_token sign-in out of scope. Confirms the HS256/JWKS mismatch is a real, known issue Supabase is working to resolve natively.
- Third-party guide (zenn.dev): confirms Supabase Custom OAuth/OIDC supports **ES256 only**; recommends "Manual configuration" (OAuth2 type) with JWKS URI left blank as a LINE workaround — not official Supabase documentation.

**Verdict:** LINE Login v2.1 **cannot be reliably configured as a Supabase Custom OIDC Provider for the web authorization-code flow** as of this revalidation, because Supabase Custom OIDC verifies via JWKS (ES256) while LINE web-login tokens are HS256 (channel secret). Mark **UNVERIFIED / NOT RECOMMENDED** for production until either:
1. Supabase releases the native LINE provider (PR #2578), or
2. A staging PoC confirms Custom OIDC works with LINE web tokens.

Whether `signInWithOAuth()` returns a normal Auth Session for custom providers: **VERIFIED YES** per official Supabase custom-oauth-providers docs (custom providers use the same `signInWithOAuth({ provider: 'custom:...' })` flow and return a normal session). This applies to custom providers generally, not specifically to LINE.

**`email_optional` / "Allow users without email":** A Supabase-side toggle for allowing users without email is mentioned only in third-party guides (not official Supabase docs). LINE returns `email` only when the `email` scope is granted and the user has a verified email. Mark **UNVERIFIED** for the Supabase custom-provider setting; handle missing email at the application level (see 6.4).

### 6.3 Recommended LINE Implementation (Staging PoC Approach)

Because Custom OIDC is unverified for LINE web login, the Phase 1A LINE implementation should use the **existing, proven custom server-side flow** (same pattern as the working legacy `authController.lineLogin()`), NOT Supabase Custom OIDC:

**Backend (New Implementation Required):**
```javascript
// POST /auth/line
// Input: { code, redirectUri, state? }

1. Verify state (if provided)
2. Exchange code for tokens:
   POST https://api.line.me/oauth2/v2.1/token
   Body: grant_type=authorization_code&code=${code}&redirect_uri=${redirectUri}&client_id=${channelId}&client_secret=${channelSecret}
   Response: { access_token, id_token, refresh_token, expires_in, token_type }
3. Verify ID Token:
   POST https://api.line.me/oauth2/v2.1/verify
   Body: id_token=${id_token}&client_id=${channelId}
   Response payload: { sub: lineId, name, picture, email, email_verified, iss, aud, exp }
   (Also validates iss = https://access.line.me, aud = channelId, exp)
4. If no id_token, fall back to GET https://api.line.me/v2/profile (Bearer access_token) → userId, displayName, pictureUrl
5. Extract: lineId = sub (or userId), name, picture, email
6. Supabase Integration (custom user creation — LINE is NOT a built-in Supabase provider):
   - Look up existing user by line_id (see 6.5 Provider Identity Strategy)
   - If exists → return existing user session (idempotent)
   - If not exists → create Supabase Auth user via supabaseAdmin.auth.admin.createUser({
       email: payload.email (may be null),
       password: random (user never uses password login),
       email_confirm: payload.email_verified || false,
       user_metadata: { line_id: lineId, name, avatar_url: picture, provider: 'line' }
     })
   - Upsert profile (id = authUser.id)
7. Return Supabase session tokens (normal session from createUser + signInWithPassword equivalent)
```

### 6.5 Provider Identity & Duplicate-Account Strategy

**Supabase-managed identities (`auth.users.identities[]`):**
- For **built-in** OAuth providers (Google, Facebook via Supabase native OAuth), Supabase auto-populates the `identities[]` array linking `provider` + `provider_id`. This provides uniqueness + account mapping out of the box — **no app-owned mirror needed for built-in providers.**
- For **LINE (custom, not built-in)**: Supabase does **not** auto-populate `identities[]`. The app must track `line_id` itself.

**Do NOT create a direct unique index on `auth.users.user_metadata->>'line_id'` (migration 006) without documented justification.** Internal `auth.*` tables are managed by Supabase; direct indexes on them are not documented as a supported app pattern and are not part of Phase 1A (code-only) scope.

**Recommended app-owned schema (if LINE mirror needed):**
- Add `profiles.line_id TEXT UNIQUE` (nullable) — app-owned, not an `auth.*` table.
- Uniqueness enforced at the `profiles` level (app-owned schema).
- **Concurrency strategy:** check-then-create inside a single transaction with `ON CONFLICT (line_id) DO NOTHING` / idempotency key, so concurrent LINE logins for the same `line_id` return the existing user (idempotent) rather than creating duplicates.
- Application guard: before create, `SELECT id FROM profiles WHERE line_id = $1`; if found, return existing session.

**Duplicate email guard (LINE & Facebook):** If `email` from provider already exists on a different account → **Return 409**, require manual linking via `/auth/link-account`. No auto-link (prevents account takeover).

### 6.6 Account Linking Guard

- Same as Facebook: if email exists on another account → **Return 409**, require manual link
- Use `line_id` for identity matching, not email

## 6A. Provider Identity & Duplicate-Account Strategy

### 6A.1 Supabase-Managed Identities (Built-In Providers Only)

For **built-in** OAuth providers (Google, Facebook via Supabase native OAuth), Supabase auto-populates the `auth.users.identities[]` array linking `provider` + `provider_id`. This provides uniqueness + account mapping out of the box — **no app-owned provider-ID mirror is needed for built-in providers.**

### 6A.2 LINE (Custom — Not a Built-In Provider)

LINE is not a built-in Supabase provider (native LINE provider PR #2578 is open, not released). Supabase does **not** auto-populate `identities[]` for LINE. The app must track `line_id` itself.

**Do NOT create a direct unique index on `auth.users.user_metadata->>'line_id'` (migration 006).** Internal `auth.*` tables are managed by Supabase; direct indexes on them lack documented justification and are out of Phase 1A (code-only) scope.

**Recommended app-owned schema:**
- Add `profiles.line_id TEXT UNIQUE` (nullable) — app-owned table, not `auth.*`.
- Uniqueness enforced at the `profiles` level.

**Concurrency strategy (prevent duplicate accounts under race conditions):**
1. Before create: `SELECT id FROM profiles WHERE line_id = $1` (idempotency check).
2. Create user + profile inside a single transaction.
3. Use `ON CONFLICT (line_id) DO NOTHING` on the profiles insert so concurrent LINE logins for the same `line_id` return the existing user rather than duplicating.
4. If a profile already exists, return the existing user's session (idempotent login).

### 6A.3 Duplicate Email Guard (LINE & Facebook)

If the provider-returned `email` already exists on a different account → **Return 409** "Email already registered. Please login with email first, then link in settings." No auto-link (prevents account takeover). Manual linking via `/auth/link-account` after ownership verification.

## 13. Supabase Session Lifecycle Design (Phase 1A Scope)

### 13.1 Sign Up
```
POST /auth/register
  → supabaseAdmin.auth.admin.createUser({ email_confirm: false })
  → Supabase sends verification email
  → Create profile
  → Return { user: profile, message: "Verify email" }
  → NO tokens returned until email verified
```

### 13.2 Sign In
```
POST /auth/login
  → supabase.auth.signInWithPassword({ email, password })
  → Returns Supabase Session { access_token, refresh_token, user }
  → Fetch profile from profiles table
  → Return { user: profile, accessToken: session.access_token, refreshToken: session.refresh_token }
```

### 13.3 Get Session (Profile)
```
GET /auth/profile (Bearer accessToken)
  → middleware verifyToken: supabaseAuth.auth.getUser(token)
  → Fetch profile
  → Return profile
```

### 13.4 Refresh Session
```
POST /auth/refresh { refreshToken }
  → supabase.auth.refreshSession(refreshToken)
  → Returns new session
  → Return { accessToken, refreshToken }
```

### 13.5 Logout
```
POST /auth/logout { revokeAllSessions?: boolean }
  → supabase.auth.signOut({ scope: revokeAllSessions ? 'global' : 'local' })
  → Return success
```

### 13.6 Expired Session
```
Middleware verifyToken gets error from supabaseAuth.auth.getUser()
  → Returns 401
  → Frontend catches 401, calls refreshAccessToken()
  → If refresh fails → logout user
```

## 17. Rollback Plan

### 17.1 Code Rollback (Git revert — source files only)

| Scenario | Rollback Action |
|----------|-----------------|

**All code rollbacks are single-file git reverts — no database changes in Phase 1A.**

### 17.2 Database Rollback (SEPARATE from code rollback)

**Database rollback is NOT a git revert.** `git revert` reverses source-code changes only; it does **not**:
- Reverse applied database migrations / schema changes
- Invalidate or repair existing Supabase Auth sessions (refresh tokens persist until expiry or explicit revoke)
- Remove rows inserted into `profiles` or `auth.users`

Because Phase 1A is code-only and no migrations are applied, there are **no database changes to roll back in Phase 1A**. If migrations 005/006 are applied in a later phase, their rollback must be handled via separate down-migration SQL (or Supabase migration rollback), coordinated with the database team — never assumed to be undone by `git revert`.

### 17.3 Session Impact of Rollback

- Reverting auth code does **not** invalidate existing Supabase sessions. Valid refresh tokens continue to work until they expire or are revoked via `supabase.auth.signOut()` / admin `signOut(userId)`.
- If a code rollback re-enables the Custom JWT fallback, legacy tokens issued before the change remain valid per their expiry.
- Plan rollback testing on staging before production; verify sessions behave as expected after revert.

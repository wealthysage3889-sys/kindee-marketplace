## Context

`GET /api/settings/public/social-config` returns `enabled=true` with all three IDs. Three defects remain:

1. LINE → `400 Bad Request - Invalid redirect_uri value`
2. Google → prompt to check "Authorized origins"
3. Web page → `Expression is of type asyncfunction, not function`

This plan fixes only the root causes below. No secrets are added to the frontend, no credentials in the
database are touched, and nothing is committed/pushed/deployed.

## 1. Root causes (one per error)

### 1.1 LINE — `400 Bad Request - Invalid redirect_uri value`

**Cause:** the `redirect_uri` the frontend sends is not registered in the LINE Login channel's
**Callback URL** list. This is a LINE Developers Console configuration gap, not a code bug.

**Evidence (no guessing):**

- `frontend/src/pages/Login.jsx:150` → `const redirectUri = window.location.origin + "/login";`
- `frontend/src/pages/Register.jsx:157` → `const redirectUri = window.location.origin + "/register";`
- Authorization URL built at `Login.jsx:159` / `Register.jsx:159` → `https://access.line.me/oauth2/v2.1/authorize?...`
- The same value is forwarded to the backend and then to LINE's token endpoint
  (`frontend/src/context/AuthContext.jsx:185-190` → `backend/controllers/authController.js:278-290`).
- Live probe `POST /api/auth/line {code:"invalid_code_probe", redirectUri:"https://kindee-marketplace.vercel.app/login"}`
  returned `401 {"message":"invalid authorization code"}` — i.e. LINE **accepted** the channel id/secret and
  failed only on the fake code. Therefore `LINE_CHANNEL_ID` / `LINE_CHANNEL_SECRET` / `LINE_ENABLED` are correct
  on the server; the only remaining mismatch is the **authorize-step redirect_uri registration**.

So the actual value sent by production is:

```
https://kindee-marketplace.vercel.app/login      (from /login)
https://kindee-marketplace.vercel.app/register   (from /register)
```

LINE requires an exact character-by-character match (scheme, host, port, path, trailing slash) — reference:
https://developers.line.biz/en/docs/line-login/web/integrate-line-login ("Setting a callback URL").

### 1.2 Google — "check Authorized origins"

**Cause:** `https://kindee-marketplace.vercel.app` is not listed in the OAuth client's
**Authorized JavaScript origins**. GIS refuses to render One Tap for an unknown origin.

**Evidence:**

- `Login.jsx:118` / `Register.jsx:128` call `window.google.accounts.id.prompt(...)`.
- `Login.jsx:121` / `Register.jsx:130` show the message
  `ไม่สามารถแสดงหน้าต่าง Google ได้ กรุณาตรวจสอบการตั้งค่า Authorized origins ใน Google Cloud Console`
  whenever `notification.isNotDisplayed() || notification.isSkippedMoment()`.
  The reported error **is this application's own string**, which proves the GIS prompt was suppressed.
- `initialize()` is called on every button click (`Login.jsx:104`, `Register.jsx:115`) — repeated
  initialization, but not the cause of the suppression.

Note: GIS One Tap only needs an **origin** (no path) and HTTPS. No "Authorized redirect URI" entry is required
for the credential flow used here (`backend/controllers/authController.js:171-173` verifies the ID token with
`audience: clientId`).

### 1.3 Web page — `Expression is of type asyncfunction, not function`

**Cause:** an `async` function is passed as the Facebook login callback. Facebook's SDK rejects it.

**Evidence (exact code path, confirmed in the shipped SDK):**

- `Login.jsx:131` and `Register.jsx:140`:
  `FB.login(async (response) => { ... }, { scope: "public_profile,email" })`
- FB SDK `sdk.Auth.login(cb, opts)` → internal `s(cb, opts)` → `sdk.ui(params, cb)`
- `sdk.ui` executes `Assert.maybeFunction(t)` on the callback
  (module `sdk.ui` in `https://connect.facebook.net/en_US/bundle/sdk.js`)
- `Assert`'s type helper does `Object.prototype.toString.call(value)` → `"[object AsyncFunction]"` →
  lowercases to `"asyncfunction"` → throws
  `AssertionError: Expression is of type asyncfunction, not function`
  (module `Assert`, same bundle — this is the **only** place in the bundle that emits that message)

Verified: the string does **not** exist in `frontend/src`, in the built bundle
(`frontend/dist/assets/index-P_Rbwsmz.js`, and the live `index-R22ISFyH.js`), in `gsi/client`, or in
`frontend/node_modules` — so it can only come from the Facebook SDK.

The Google callback at `Login.jsx:106` / `Register.jsx:117` is also `async`, but Google's `gsi/client` performs
no such assertion (no matching string in that script), so it is not implicated. It will be kept as-is per the
chosen approach.

## 3. Code changes (file → change → reason)

### 3.1 `frontend/src/pages/Login.jsx`

| Location | Change | Reason |
|---|---|---|
| `handleFacebook` (126-145) | Replace `FB.login(async (response) => {...})` with a **non-async** callback; do the async work inside via `.then()/.catch()` (or a nested `async () => {}` IIFE that is not the SDK callback) | Fixes error 1.3 — `Assert.maybeFunction` rejects `AsyncFunction` |
| `loadFacebookSdk` (15-23) | Bump `version: "v19.0"` → a currently supported Graph version (e.g. `v23.0`); keep the same loader logic | `assertValidVersion` only checks `^v\d+\.\d\d?$`, but a 2023-era version is near/after Graph API support; low-risk hygiene, not the root cause |
| `handleGoogle` (94-124) | Guard `google.accounts.id.initialize(...)` with a `useRef` so it runs **once**; keep the existing custom button; replace the generic info text with `notification.getNotDisplayedReason()`-based diagnostics | Implements the chosen option 1; removes repeated initialization and makes the origin problem explicit instead of a generic hint |
| `SocialAuth` usage (199) | No change to the `SocialAuth` component structure | User constraint |

### 3.2 `frontend/src/pages/Register.jsx`

Same two changes (`handleFacebook` callback, `handleGoogle` one-time init + diagnostics) at lines
`135-152`, `105-133`, and `loadFacebookSdk` at `18-26`. `handleLine` at `154-160` stays as-is.

### 3.3 `frontend/src/components/SocialAuth.jsx`

- Remove the unused imports `useEffect` (line 1) and `useLocation` (line 2).
- No structural/visual change to the rendered buttons.

### 3.4 `backend/controllers/authController.js`

- `googleLogin` (158-203): wrap `client.verifyIdToken(...)` in `try/catch` and return
  `400 { success:false, message:"Google credential ไม่ถูกต้อง" }` on failure.
  Evidence of the current defect: probe `POST /api/auth/google {credential:"invalid"}` returns
  `500 {"success":false,"message":"Wrong number of segments in token: invalid"}` — an unhandled
  `google-auth-library` error leaking internals and mis-reporting a client error as a server error.

No other backend change. `facebookLogin` / `lineLogin` already handle their token failures correctly
(probe results: `401 Facebook token ไม่ถูกต้อง`, `401 invalid authorization code`).

### 3.5 Explicitly **not** changing

- No `renderButton()` for Google (user constraint).
- No change to `GoogleAuthWrapper.jsx` / `GoogleSignInButton.jsx` (dead code — `GoogleSignInButton` is unused).
- No change to `AuthContext.jsx` (token flow already correct: `applySession(mode, data.token, data.user)`).
- No credential/DB changes; no new frontend secrets.
- `state` stays `"line_login"` / `"line_register"` (LINE recommends a random per-session value — noted as a
  follow-up, not required to fix the reported errors; `nonce` is optional per LINE docs).
